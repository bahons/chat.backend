# B05.2 — API Contracts, Authentication Hardening & Sync Recovery

## Role and input
You are Codex working **only in `chat-backend`** (C#, ASP.NET Core, EF Core, PostgreSQL, SignalR). Read `AGENTS.md`, `docs/implementation-status.md`, `docs/architecture.md`, `docs/security.md`, `docs/contracts/api-v1.md`, `docs/contracts/events-v1.md`, the actual endpoints and tests before changing code. The audit is the baseline, not proof that B05.1 has been completed. Inspect the current working tree and report any unresolved B05.1 blocker.

## Goal / scope
Fix audit findings **API-01, AUTH-01, AUTH-02, SYNC-01** while preserving established B01–B05 flows and B2C ACL. Deliver a machine-readable, verified contract so `chat-frontend` and `chat-mobile` can implement against the same API. Do not implement B06, monetization or unrelated features.

## 1. API-01 — OpenAPI accuracy
- Compare *runtime behavior* of all current B01–B05 endpoints with `artifacts/openapi.json` and `docs/contracts/api-v1.md`; correct declaration **in the source** and regenerate the artifact. Include mandatory `X-Application-Draft` header on verification-document upload; valid response shapes and the observed `404`, `409`, `413`, `415`, `503` responses; `MEDIA_NOT_READY`; and any other verified status. Do not document `429` where rate limiting is disabled.
- Give public roles, document states, verification states and other bounded fields explicit schemas/enums without changing existing serialized values. Separate public errors from internal details, including neutral responses for sensitive account existence checks. Never expose secrets or staff author IDs through response schemas.
- Add contract tests against running endpoints with a realistic DB to check representative happy/error cases, mandatory header and enum values; snapshot-to-snapshot equality alone is insufficient. Check schema validity with an OpenAPI validator and document what it does not cover.
- Add deterministic schema generation instructions; identify **additive vs breaking** changes and update `docs/contracts/api-v1.md`, version notes and consumer handoff.

## 2. AUTH-01 — login abuse protection and lock contention
- Examine current IP-only, process-local limits and proxy trust policy. Implement abuse protection using both normalized account identifier and trusted client network address, with a bounded retry strategy suitable for one instance and an explicit multi-instance path. Do not trust user-supplied forwarded headers from arbitrary peers.
- Avoid doing password hash verification under a long-held row lock; preserve security (no time-of-check races for account state / token issuance) and safe concurrent operations; never log passwords, credentials, full JWT or refresh token values. Use consistent external authentication errors to avoid disclosing whether accounts exist.
- Test failed logins from multiple IPs against one account, many accounts from one IP, allowed recovery, trusted vs forged forwarding, concurrency with refresh/reset and throttling behavior. Avoid accidental permanent lockout or unbounded memory growth.

## 3. AUTH-02 — refresh token coordination
- Keep existing rotation, hash-at-rest and replay detection; do not silently remove replay revocation or accept stale refresh tokens indefinitely.
- Define server/client refresh behavior and document **single-flight refresh required in clients**. Explicitly handle two concurrent refresh requests and a lost response after successful DB commit: distinguish expected security outcome from UX trade-off. If changing server semantics (e.g. tightly bounded idempotency), justify threat model and cover it with tests; otherwise retain replay policy and specify reauthentication behavior in the contract.
- Test concurrent refresh, sequential replay, logout/reset, expired/revoked family, and refresh-error semantics. Ensure transactions and row locks have bounded duration.

## 4. SYNC-01 — reconnect and read state
- Choose a minimal additive REST contract returning stored per-side read position/receipt **only for authorized conversation participants**, sufficient to restore both-side read state after reconnect. Keep read timestamps/positions monotonic.
- Update DTOs/queries, `docs/contracts/api-v1.md`, `docs/contracts/events-v1.md` if relevant, and sample payloads. Avoid exposing individual staff identity to clients and avoid leaking another conversation's data.
- Test missed SignalR events -> REST resync; cross-tenant/cross-conversation `403/404`; read racing with new messages; consistent read state on list/detail as appropriate. Document how clients reconcile out-of-order events.

## Shared constraints
- **B2C only**: `CLIENT` initiates conversation; only verified active companies appear in the directory; company signup and verification remain web-only; company staff can work from mobile and web.
- All functions are free in the current release; preserve future monetization documentation only.
- Maintain compatibility with `chat-frontend` / `chat-mobile`. Never edit their repos from this task. If an unavoidable breaking change is proposed, **stop and present a migration plan**, do not implement it without approval.
- Use EF Core migrations for schema changes; no destructive migrations or silent data deletion. Respect existing `chat.*` project naming.
- Add no new production dependency without rationale and security impact. Avoid exposing implementation details in auth errors.

- Existing B01–B05 tests still pass and no regression of auth, ACL, upload or messaging.
