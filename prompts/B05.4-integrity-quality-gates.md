# B05.4 — Data Integrity, Business Recovery, Retention & Release Gates

## Role and prerequisite
You are Codex in **`chat-backend`**. Read `AGENTS.md`, `docs/implementation-status.md`, latest `docs/hardening/B05.1-results.md` / `B05.2-results.md` / `B05.3-results.md` if present, all `docs/contracts/*`, `docs/data-model.md`, `docs/testing-and-release.md`, `docs/security.md` and the implementation. Audit is a baseline, not a claim that earlier fixes have been delivered. Preserve current C# ASP.NET Core + EF Core + SignalR architecture and project name `chat`.

## Scope
Close **BIZ-01** and P3 issues: relational integrity, inbox pagination, retention, Expo device registration ownership, CI/security checks, layer boundaries and missing negative tests. Complete end-to-end readiness review for B01–B05. Do not add monetization, B06 or unrelated product features.

## 1. BIZ-01 — rejected registration and identifier reservation
- Design an explicit web-only re-application / restoration flow for rejected business applications, preserving full moderation history and preventing unauthenticated parties from permanently reserving another company's country+registration number.
- Review uniqueness constraints for `Country, RegistrationNumber` and normalized email; distinguish draft, pending, rejected, verified, suspended. Do not allow two verified businesses to own one identifier. Document identity proof, recovery, moderation and dispute handling.
- Do not automatically free/overwrite an active verified company's legal identifiers or leak whether an email/registration ID exists via public error details. Check 409 semantics and enumeration resistance.
- Write migrations safe for existing data with explicit backfill/rollback plan. Test new and rejected applicant flows, fraudulent claim attempt, concurrent approval/reapply, audit trail and non-disclosure.

## 2. P3 DB integrity and pagination
- Enforce business domain invariants at persistence level where feasible: conversation client must have `UserKind=CLIENT`, attachment/receipt `MessageId` must belong to same `ConversationId`; propose triggers/checks/composite FKs where ordinary FKs cannot express invariants. Describe trade-offs; test invalid direct SQL inserts, EF writes and migration from current dataset. Never block required historical rows without a verified migration strategy.
- Fix inbox pagination that currently depends on mutable `UpdatedAt` and can skip/duplicate items when new messages arrive. Choose stable snapshot cursor or documented keyset semantics; expose cursor validation, ordering guarantees, tie breakers and reconnect reconciliation. Do not silently break existing cursor format; version it if necessary.
- Test concurrent messages between pages, tied timestamps, deletes/suspension, invalid cursor, no cross-tenant leakage.

## 3. P3 retention/privacy and media lifecycle
- Define a documented data-retention table for refresh sessions, used/revoked tokens, submitted verification documents, completed Outbox, push jobs, uploads/attachments and message copies in Outbox; propose defaults as configurable policies, **do not guess legal retention mandates**.
- Implement safe background deletion and bounded batches respecting legal hold/active references and backup behavior. Never silently delete user message history or required legal/verification evidence; require approval for destructive production retention settings. Cover data/objects together and provide reconciliation/metrics.
- Remove or minimize duplicate message body persisted in delivery queues when not strictly required; restrict access and log redaction. Cover failed cleanup, resume, idempotency and isolation.

## 4. P3 Expo device reassignment
- Review current upsert of a pre-existing Expo token that can reassign device ownership. Implement a defensible policy for account switching, stolen push token and logout. Tie registration to authenticated sessions, prevent hijacking where possible, expire/remove old links and avoid exposing sensitive content in push payloads. Document push-token limitations (possession is not a strong identity proof).
- Test token re-use by another account, stale/revoked session, logout, concurrency and push delivery to previous owner.

## 5. CI, architecture boundaries, negative tests
- Add practical CI gates: clean restore/build/test/format, migrations/snapshot, OpenAPI diff against published baseline (with breaking-change detection), secret scanning, dependency vulnerability checks including **runtime/container** images, SAST where available; fail closed on meaningful findings and document scanner limitations. Avoid exposing security tokens in CI logs.
- Review migration of use cases currently placed in `chat.Api` into `chat.Application` / `chat.Domain` while retaining thin API endpoint orchestration; perform incremental non-breaking refactor only where it improves testability, avoid wholesale rewrite.
- Add negative/contract tests from audit: JWT issuer/audience/expiry, concurrent refresh, TLS-proxy authenticated SignalR smoke where possible, `LeaveConversation`, `SetTyping`, `ConversationReadUpdated`, `BusinessAccessRevoked`, actual JS and React Native consumer compatibility (if repos unavailable, prepare runnable consumer contract harness and mark cross-repo checks pending).
- Keep all future monetization documented but **disabled**; business registration/verification **web-only**, company staff web/mobile login; B2C communications only.

## 6. Final B01–B05 acceptance matrix
- For every original audit issue (P1, P2, P3), record ID, severity, finding, code/tests evidence, disposition (`FIXED`, `ACCEPTED-LIMITATION`, `OPEN`) and release blocking status. Do not conflate passing unit tests with production verification.
- Include separate assessment for single vs multiple API replicas, HTTPS/reverse proxy, production runtime patch, database restore drills, real Expo delivery, MinIO + ClamAV environment, SMTP failure/retry, contract sync to both consumer repos.
- Flag any uncovered P1 as explicit NO-GO for public launch. P2 accepted risks must have owner/mitigation and revisit trigger. If an unavoidable breaking API change emerges, **stop for approval** rather than silently changing consumers.
