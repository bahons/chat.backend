# Контракт REST API — chat (v0.5.0)

**Статус:** B01–B05 реализованы в backend. Маршруты этапов 2 и 3 описывают планируемый контракт.

**Источник истины после реализации:** `backend` (ASP.NET Core Web API) — OpenAPI, экспортируемый из кода и проверяемый CI.  
**Синхронизация:** одинаковая копия этого файла в `backend`, `frontend`, `mobile`. При изменениях повышать версию и обновлять все потребители в отдельных PR.

В 0.3.0 добавлены `readState` и `scanStatus`. OpenAPI описывает существующие ошибки, обязательный заголовок загрузки, бинарные тела и допустимые строковые значения. `/v1`, существующие поля и значения сохранены. Вход может вернуть `429` по нормализованному email даже при смене IP.

В 0.4.0 добавлены временные ответы `503 INTERNAL_ERROR` при невозможности поставить запрос в очередь.
Существующие маршруты, успешные ответы и формы запросов сохранены.
В 0.5.0 добавлена повторная веб-заявка владельца. Новые страницы inbox возвращают курсор `v2.`.
Операции с Expo-токеном учитывают владельца и явную передачу.

## Базовые правила

- Base URL: `https://<api-host>/v1` (домены окружений через `.env`, не хардкодить).
- JSON: `camelCase`, даты в ISO 8601 UTC, id — UUID, HTTP over TLS.
- `Authorization: Bearer <accessToken>`; refresh-токен имеет ротацию и отзывание. Не пересылать токены в URL.
- Ошибки: `{ "error": { "code": "FORBIDDEN", "message": "...", "requestId": "...", "details": null } }`. Коды: `VALIDATION_ERROR`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `RATE_LIMITED`, `VERIFICATION_REQUIRED`, `SUSPENDED`, `MEDIA_NOT_READY`, `INTERNAL_ERROR`.
- Пагинация: `?cursor=<opaque>&limit=20`, ответ `{ "items": [...], "nextCursor": null | "..." }`; стабильная сортировка по времени + id.
- `userKind`: `CLIENT` | `BUSINESS_MEMBER` | `PLATFORM_ADMIN`. `businessRole`: `OWNER` | `ADMIN` | `AGENT`. Роли не определяют тип диалога: участники диалога всегда `clientUserId` и `businessId`.
- Клиент общается **только** с верифицированной активной компанией; ни `CLIENT↔CLIENT`, ни `BUSINESS↔BUSINESS` эндпоинтами не поддерживаются. Сотрудник отвечает от имени компании; личный id оператора не раскрывается клиенту.
- MVP: клиент первым создаёт диалог. У компании нет API для массовых/непрошеных исходящих сообщений. Это зафиксированное рабочее допущение до отдельного продуктового решения.
- MVP: доступ бесплатный для всех. Биллинг, планы, платежи и лимиты тарифов **не реализовывать**; сохранить в документации как future.

## Авторизация и аккаунты — Этап 1

| Метод | Маршрут | Кто | Назначение |
|---|---|---|---|
| `POST` | `/auth/client/register` | Гость | Регистрация клиента: email + пароль + displayName |
| `POST` | `/auth/login` | Гость | Login: email + пароль; ответ с токенами и `userKind` |
| `POST` | `/auth/refresh` | Сессия | Ротация refresh-токена |
| `POST` | `/auth/logout` | Авторизован | Отозвать refresh-сессию |
| `POST` | `/auth/email/verify` | Гость с токеном | Подтверждение email |
| `POST` | `/auth/password/forgot` | Гость | Запрос сброса пароля без раскрытия существования учётки |
| `POST` | `/auth/password/reset` | Гость с токеном | Смена пароля |
| `GET` | `/me` | Авторизован | `{id, userKind, displayName, email, emailVerified, businessMemberships[]}` |

Запросы передаются JSON. Регистрация принимает `{email,password,displayName}`, login принимает
`{email,password}`, refresh принимает `{refreshToken}`, verify принимает `{token}`, forgot принимает
`{email}`, reset принимает `{token,password}`. Login и refresh возвращают
`{accessToken,refreshToken,expiresAt,userKind}`. Регистрация и forgot возвращают `202` с пустым телом.
Verify, reset и logout возвращают `204`. Logout отзывает семейство сессии из Bearer JWT.
Успешный `202` означает принятие запроса. Если требуется письмо, оно поставлено в очередь вместе с изменением аккаунта. При переполнении или временной недоступности очереди сервер возвращает `503`, в том числе для неизвестного email. Повторите запрос позже. SMTP-подтверждение отдельно от ответа API.
Для нового пароля требуется 15–128 символов. Access token действует 10 минут, семейство refresh
по умолчанию действует 30 дней от входа. Повтор старого refresh отзывает всё семейство.
Токены передаются в теле JSON и в Authorization. Backend API не выдаёт auth cookies.

- Вход с неверными данными, неизвестным email или отключённой учёткой возвращает `401 UNAUTHENTICATED`. `403 VERIFICATION_REQUIRED` возможен после проверки правильного пароля. Регистрация клиента и запрос сброса возвращают одинаковый `202` независимо от существования email.
- При `429 RATE_LIMITED` выдержите `Retry-After` в секундах, когда заголовок присутствует. Для окна входа действуют лимиты по нормализованному email и адресу клиента. `503 INTERNAL_ERROR` сообщает о временной недоступности обработки без деталей инфраструктуры.
- **Single-flight refresh обязателен.** Для одного семейства отправляйте один запрос ротации, пока остальные операции ждут его результат. После `200` атомарно замените оба токена. При `401` очистите сессию и запросите повторный вход. Если результат refresh неизвестен из-за разрыва, таймаута или ошибки с неопределённым исходом, не повторяйте запрос со старым токеном и запросите повторный вход.
- Если два запроса одновременно используют один токен, первый может вернуть `200`. Второй получает `401` и отзывает семейство, включая токены из первого ответа. Если сервер зафиксировал ротацию, а ответ потерялся, повтор старого токена имеет тот же эффект. Просроченный, неизвестный или отозванный refresh возвращает нейтральный `401`.

Выбранный для MVP способ регистрации клиента — **email/пароль**. Телефонный OTP пока не утверждён и не входит в этот baseline. Mobile не содержит бизнес-регистрации; компания и её владелец создаются **исключительно в веб-сценарии** подачи заявки. Backend проверяет бизнес-правила, документы и статус; полагаться на `User-Agent`/CORS для защиты регистрации нельзя.

## Регистрация компании, проверка, каталог — Этап 1

| Метод | Маршрут | Кто | Назначение |
|---|---|---|---|
| `POST` | `/business-applications` | Гость | Веб-регистрация компании и owner, заявка `PENDING_VERIFICATION` |
| `GET` | `/my-business` | OWNER / ADMIN | Профиль и состояние заявки своей компании |
| `POST` | `/my-business/{id}/applications` | OWNER | Новая веб-заявка после отклонения с новым черновиком и документами |
| `PATCH` | `/my-business` | OWNER / ADMIN | Разрешённые поля бизнес-профиля |
| `GET` | `/businesses` | CLIENT | **Только** `VERIFIED` + `ACTIVE`, поисковая строка `q`, `cursor`, `limit` |
| `GET` | `/businesses/:businessId` | CLIENT | Только публичный профиль верифицированной активной компании |
| `GET` | `/admin/business-applications` | PLATFORM_ADMIN | Очередь проверки, фильтр по статусу |
| `GET` | `/admin/business-applications/:id` | PLATFORM_ADMIN | Детали заявки и приватных файлов |
| `POST` | `/admin/business-applications/:id/decision` | PLATFORM_ADMIN | `{decision:"APPROVE"|"REJECT",reason?}`; audit trail |

`POST /business-applications`: `{ owner: {email,password,displayName}, business: {legalName,displayName,registrationNumber,country,category,description?}, verificationDocumentIds: [] }`. Заявка также требует `applicationDraftToken` и от одного до пяти документов.

1. `POST /business-applications/drafts` выдаёт `{draftId,applicationDraftToken,expiresAt}` на 30 минут.
2. `POST /business-applications/drafts/{id}/documents` принимает сырые байты PDF, JPEG или PNG
   до 5 МиБ и обязательный заголовок `X-Application-Draft`. Ответ `200` содержит
   `{id,contentType,size,scanStatus:"PENDING"}`. Отсутствующий или недействительный токен даёт `404`,
   превышение числа документов даёт `409`, размера тела — `413`, неподдерживаемый MIME — `415`.
3. `POST /business-applications` закрывает черновик и возвращает `200` с подтверждением
   приёма `{id,businessId,status:"PENDING_VERIFICATION"}`. При уже используемом email ответ
   имеет ту же форму, а учётка и заявка не создаются. Идентификаторы подтверждения непрозрачны.
   Наличие заявки и её состояние доступны владельцу после входа. Незавершённая заявка
   не резервирует реквизиты. Конфликт подтверждённого владения даёт нейтральный `409 CONFLICT`
   только в административном решении.
4. Только платформенный администратор может скачать файл через
   `GET /admin/business-applications/{id}/documents/{documentId}`. Ответ содержит байты
   `application/octet-stream` и заголовок `Content-Disposition`.
   Эти документы хранятся в закрытой таблице PostgreSQL отдельно от файлов диалогов. После загрузки
   документ ожидает проверку ClamAV. Детали заявки показывают `scanStatus` каждого документа
   со значением `PENDING`, `READY` или `QUARANTINED`.
   Скачать можно только READY. В остальных случаях скачивание возвращает `404`.
   Одобрение заявки при наличии файла, который ещё не готов, возвращает `409 MEDIA_NOT_READY`.

Платформенный администратор может приостановить проверенную компанию через
`POST /admin/businesses/{id}/suspend` с `{reason}`. `GET /my-business` показывает статус владельцу
до одобрения. `PATCH /my-business` доступен активному OWNER/ADMIN проверенной компании.
Для нескольких memberships передайте `businessId` в query.

Каталог принимает поиск по названию или категории. Непустой `q` после обрезки пробелов
должен содержать 3–100 символов. Публичные карточки содержат только `id`, `displayName`,
`category` и `description`.

Состояния бизнеса: `PENDING_VERIFICATION`, `VERIFIED`, `REJECTED`, `SUSPENDED`. В публичном поиске отображается только `VERIFIED` и активный профиль. Владелец может видеть статус в вебе до проверки, но не использовать мобильный бизнес-режим до `VERIFIED`.

Для повторной заявки владелец с подтверждённой учёткой готовит новый черновик и отправляет
`{verificationDocumentIds,applicationDraftToken}` в `POST /my-business/{id}/applications`.
Ответ `200` содержит новый id заявки и прежний business id. Чужая компания возвращает
`404`, недоступное состояние даёт `409`. Предыдущая заявка, её решение и документы
сохраняются. `VERIFIED` и `SUSPENDED` проходят отдельный административный процесс спора.

## Диалоги и сообщения — Этап 1

| Метод | Маршрут | Кто | Назначение |
|---|---|---|---|
| `POST` | `/conversations` | CLIENT | `{businessId}`; вернуть существующий или создать единственный диалог на пару |
| `GET` | `/conversations` | CLIENT / BUSINESS_MEMBER | Список только доступных диалогов, `cursor`, `limit` |
| `GET` | `/conversations/:id` | Участник | Метаданные, права и статус |
| `GET` | `/conversations/:id/messages` | Участник | История по cursor, упорядочена стабильно |
| `POST` | `/conversations/:id/messages` | Участник | `{clientMessageId,type,text?,attachmentIds?}`; идемпотентность |
| `POST` | `/conversations/:id/read` | Участник | `{lastMessageId}`; обновить состояние прочитанного |
| `POST` | `/uploads/presign` | Участник | Начать безопасную загрузку изображения/документа (phase 1) |
| `POST` | `/uploads/:uploadId/complete` | Владелец upload | Завершить с проверкой объекта и метаданных |

`POST /uploads/presign` принимает `{conversationId,contentType,size}` и возвращает
`{uploadId,uploadUrl,expiresAt,headers}`. Подписанный PUT действует 5 минут. Клиент передаёт
точные `Content-Type` и длину тела. Поддерживаются PDF, JPEG и PNG до 10 МиБ. Complete проверяет
длину, MIME и результат сканирования, затем возвращает `{uploadId,status}`. Только `READY`
разрешает привязку к сообщению. `complete` также может вернуть `QUARANTINED` или
`409 MEDIA_NOT_READY` при просроченной загрузке, отсутствии объекта или несовпадении метаданных.
Завершить загрузку можно в исходном семействе сессии до истечения PUT-ссылки плюс 10 минут.
При `503` от сканера или хранилища загрузка остаётся `PENDING`. Повторите `complete` до дедлайна.
Участник может запросить минутную ссылку на прикреплённый файл через
`GET /attachments/{id}/download`. Ответ `{downloadUrl,expiresAt}`.
Уже выданная GET-ссылка сохраняет доступ до истечения срока. PUT-ссылка позволяет запись только во временный объект.

`POST /devices` с `{pushToken}` регистрирует токен Expo за текущим семейством сессии и возвращает
`{id}`. Другой аккаунт получает нейтральный `409`, пока прежний владелец явно не выполнит
`DELETE /devices/{id}`. При смене аккаунта вызовите DELETE до logout, затем зарегистрируйте
токен с новой сессией. Logout прекращает доставку по старому семейству и сохраняет привязку.
При отсутствии доступа к прежнему аккаунту требуется новый push-токен или восстановление учётки.

В MVP `type=TEXT|IMAGE|FILE`. `AUDIO|VIDEO` как типы вложений добавляются в Этапе 2. Отправка ссылки на несуществующий/чужой/неготовый attachment запрещена. `clientMessageId` — UUID, уникальный в пределах автора/диалога; повторный запрос возвращает ранее созданное сообщение без дубля. При отсутствии доступа использовать одинаково аккуратный `404` или `403`, не раскрывающий чужие диалоги.

При насыщении Outbox отправка нового сообщения или обновление отметки прочтения возвращает `503` до сохранения записи. При повторе отправки используйте тот же `clientMessageId`.

Пример `Message`: `{id,conversationId,clientMessageId,authorSide:"CLIENT"|"BUSINESS",type:"TEXT",text:"Здравствуйте",attachments:[],createdAt,editedAt:null}`. Отдельный внутренний `authorUserId` хранится в БД, но не выдаётся клиенту для сообщений от бизнеса.

Создание диалога, список и детали возвращают одинаковую структуру `readState`.
Новая выгрузка списка идёт по неизменным `createdAt DESC, id DESC`. Курсор `v2.` непрозрачен.
Продолжение по старому 32-символьному курсору сохраняет прежний порядок до конца выгрузки.
Для стабильного обхода начните заново без курсора. ACL пересчитывается на каждой странице.
Изменение сообщения не перемещает строку между новыми страницами. Новые диалоги, удаление,
suspension и смена прав могут изменить состав выдачи. После reconnect обновите первую страницу,
выполните REST resync и при необходимости упорядочьте видимые карточки по `updatedAt` в UI.
Сторона, которая ещё не отмечала сообщения, представлена `null`. Позиция бизнеса общая для сотрудников
с доступом к диалогу. Поле не содержит идентификатор сотрудника.

```json
{
  "readState": {
    "client": {
      "lastMessageId": "b73056de-322f-4574-9382-6726d3e49b50",
      "updatedAt": "2026-11-08T10:14:00Z"
    },
    "business": null
  }
}
```

`POST /conversations/{id}/read` возвращает `{conversationId,readerSide,lastMessageId,updatedAt}`.
Повторная или более старая позиция возвращает уже сохранённое значение с прежним временем.
Сервер сортирует сообщения по `createdAt` и `id`. Чужой диалог или сообщение из другого
диалога возвращают `404`. После восстановления SignalR перечитайте список, детали открытого
диалога и историю сообщений. Применяйте правила слияния из [контракта событий](events-v1.md).

## Health

`GET /health/live` возвращает `200` с `{"status":"healthy"}`.
`GET /health/ready` возвращает тот же ответ при готовности или `503 INTERNAL_ERROR` при проблемах
с БД, миграциями или критической конфигурацией. Rate limiting для обоих маршрутов отключён.
