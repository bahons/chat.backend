# Backend: безопасность, верификация, приватность

## Границы доверия

- Public: регистрация клиента, вход, **веб-заявка бизнеса**; protection: rate limit, captcha/abuse defense where needed, проверка email, валидация юридических атрибутов и документов.
- Authenticated CLIENT: каталог VERIFIED, собственные диалоги; запуск нового диалога только со VERIFIED+ACTIVE.
- Authenticated BUSINESS_MEMBER: только свой бизнес, собственные доступные диалоги, запрет мобильного доступа до бизнес-верификации. OWNER/ADMIN/AGENT — минимально необходимые полномочия.
- PLATFORM_ADMIN: создаётся только защищённой административной процедурой (seed/CLI/manual invite) и может проводить review; не публичная self-signup роль. Все решения журналировать.
- Нельзя доверять скрытым UI-кнопкам: middleware/guards/DB checks обязательны для **каждого** endpoint и SignalR Hub methods.

## Веб-только регистрация бизнеса

Продуктовое требование означает: mobile UI не имеет регистрации бизнеса, а официальный onboarding-сценарий доступен только через web. Но серверный endpoint публичной веб-заявки технически может вызвать любой HTTP-клиент. Не пытаться выдавать `User-Agent`, `Origin`, referer или CORS за надёжное доказательство, что заявка создана веб-браузером. Реальная защита — верификация, anti-abuse и выдача прав лишь после проверки.

## Аутентификация

- Пароли — Argon2id или сопоставимый современный KDF; strong password policy; сброс одноразовым short-lived токеном.
- B01 использует ASP.NET Core Identity PasswordHasher в формате IdentityV3 с PBKDF2-HMAC-SHA512 и 210 000 итераций. Встроенный формат включает соль и параметры и позволяет повышать стоимость при успешном входе.
- JWT access short-lived; refresh-токен rotation + hash-at-rest + replay detection + revoke chain. Для SignalR transport проверить поведение `access_token`: если библиотека помещает токен в query во время WebSocket handshake, принимать его только на Hub path, требовать WSS и исключить query-string из логов.
- Web: refresh предпочтительно в `Secure; HttpOnly; SameSite` cookie с CSRF-защитой при cookie-auth; access token по выбранной безопасной схеме, не хранить долгоживущие секреты в localStorage.
- Mobile: токены в системном secure storage; не AsyncStorage. Все API через TLS/WSS.
- В вебе и мобильных клиентах корректно обрабатывать expired/rotated token, session revocation, role change.

### Ограничения входа и ротация B05.2

- До PBKDF2 действуют два счётчика допуска входа. Ключ аккаунта — SHA-256 нормализованного email. Ключ сети — адрес соединения после обработки заголовков от доверенного reverse proxy. Попытки учитываются независимо от результата проверки пароля, существования аккаунта и его статуса.
- По умолчанию допускаются 8 запросов на аккаунт и 10 на адрес за 60 секунд. Лимит ключей каждого счётчика — 4096. При заполнении новый ключ получает `429` до сброса окна, при этом заблокированный запрос не расходует второй лимит. Общий HTTP-лимит и лимит группы auth действуют отдельно.
- Настройки `Identity__LoginAttemptsPerAccount`, `Identity__LoginAttemptsPerAddress`, `Identity__LoginWindowSeconds` и `Identity__LoginKeyCapacity` применяются к одному экземпляру. Перезапуск сбрасывает счётчики. Для нескольких экземпляров требуется общий атомарный лимитер, например операция Redis, проверяющая оба ключа и общий предел активных ключей до увеличения счётчиков, с TTL для окна и общим `Retry-After`. Следует отдельно проверить сбои общего хранилища и правила доверия к прокси перед масштабированием.
- Проверка и обновление хеша выполняются до блокировки строки. При захвате блокировки проверяются актуальные состояние аккаунта, email, хеш либо токен сброса. Выдача сессии и отзыв при сбросе сериализуются по строке пользователя.
- PostgreSQL ограничивает ожидание блокировки 2 секундами, отдельный запрос в транзакции 5 секундами и простой внутри транзакции 10 секундами. Таймаут захвата строки возвращает нейтральный `503`.
- Refresh хранится в виде SHA-256 хеша. Повтор использованного токена активного семейства отзывает это семейство. Клиенты обязаны выполнять single-flight и повторно аутентифицировать пользователя при неопределённом результате ротации. Это сохраняет защиту от replay ценой повторного входа при потере успешного ответа. [RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2)

## Верификация бизнеса

- Документы private, upload signed URL краткоживущие; malware scanning или явно документированный безопасный карантин в MVP.
- B05.1 сканирует документы через ClamAV после базовой проверки формата. Только READY разрешает скачивание и одобрение заявки. Ошибка сканера сохраняет PENDING для повтора.
- Результат review с `actor, when, decision, reason`; business profile не показывать в каталоге до APPROVE.
- Проверка регистрационных документов может зависеть от страны. Не заявлять автоматическую юридическую верификацию без интеграции и правил юрисдикции.
- Suspended company скрывается из поиска; отправка сообщений блокируется по серверной политике; сообщить существующим клиентам нейтральную причину недоступности.

## Медиабезопасность

- Проверять MIME по содержимому, размер, extension, ownership, allowed types. Изолировать storage ключи и private URLs, ограничивать TTL и привязывать выдачу к ACL диалога.
- Нельзя публиковать verification docs в том же бакете/префиксе, что пользовательские вложения без разделения политик.
- Ограничить URL previews и загрузку внешних ссылок, чтобы не открыть SSRF.

### B05.3

- SignalR проверяет действующее семейство JWT, состояние пользователя и ACL перед передачей данных. Периодический обход закрывает соединения после устойчивого отзыва доступа. Событие suspension не отправляет ID бизнеса или причину.
- S3-ссылки остаются действительными до истечения срока. GET действует до минуты, PUT до пяти минут. Уже начатая загрузка может продолжиться после дедлайна. Для нового URL выполняется текущая проверка ACL, между проверкой и выпуском URL остаётся окно. PUT пишет во временный ключ. Complete проверяет исходное семейство и актуальные права, а повторное сканирование и дедлайн ограничивают обработку старых объектов. [Документация S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html#PresignedUrl-Expiration)
- Mail intent хранит зашифрованный токен AES-256-GCM со случайным nonce и привязкой к ID намерения, ID пользователя и типу письма. Адрес, письмо и токен в plaintext не входят в метаданные очереди. Стабильный ключ `AccountEmail__QueueKeyBase64` храните отдельно от БД и JWT в secret manager. После завершения ciphertext удаляется из рабочей записи. Резервные копии сохраняют прежние данные до окончания retention.
- Для ротации mail key остановите приём новых запросов, дождитесь завершения активной очереди со старым ключом, остановите процесс и замените ключ. При компрометации старого ключа подавите прежние намерения, обнулите соответствующие одноразовые коды контролируемой операцией и запросите выпуск новых. Утрата ключа ведёт к dead letter для нечитаемых намерений.

## Не забыть к production

### B05.4

- Публичная заявка не раскрывает занятый email или регистрационный номер через статус и форму ответа. Предварительные заявки не резервируют реквизиты. Подтверждённое владение защищено уникальным индексом и ручной проверкой. [Процесс восстановления и споров](hardening/B05.4-results.md)
- Expo-токен не подтверждает личность. Действующий владелец явно освобождает токен, передача другому аккаунту выполняется атомарно, а logout оставляет старое владение и отключает доставку. После release украденный токен остаётся риском, поэтому храните токен как секрет и используйте новый при подозрении на компрометацию.
- Retention включается после согласования владельцем данных, а hold действует на scheduled cleanup. Внешние lifecycle rules, backups и восстановление проверяются отдельно. [Таблица retention](data-model.md#retention-b054)

Threat model, OWASP ASVS/MASVS relevant guidance, dependency/SAST/secret scans, audit, abuse reports/blocking, rate limits per actor and IP, backups + restore test, secret rotation, data residency/legal review, retention/deletion/export policies, monitoring without PII.
