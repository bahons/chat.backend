# Технический аудит B01–B05

Аудит выполнен 8 ноября 2026 года. Проверена рабочая копия `chat-backend` на базе `bea2bdc`. Изменения B01–B05 на момент проверки находятся в рабочей копии. Объём аудита включает `AGENTS.md`, все документы в `docs/`, реализацию, миграции, OpenAPI, тесты и локальную Git-историю. По результатам добавлен этот отчёт.

**Состояние на момент исходного аудита.** Основные сценарии работали на локальном стеке. Перед публикацией в интернете нужно устранить проблемы с обязательностью TLS и обработкой документов верификации, проверить патч runtime и привязать готовность API к схеме БД. Зелёный прогон подтверждает проверенные сценарии, включая изоляцию диалогов, но не закрывает эти проблемы.

## B05.1 — Security & Readiness

| Пункт | Изменение и подтверждение |
| --- | --- |
| TLS-01 | Production отклоняет HTTP до аутентификации. При настройке reverse proxy требуется реальный TLS до Kestrel, точный IP непосредственного прокси и одна пара проверенных forwarded headers. На локальном Nginx 1.28.3 с отдельными сертификатами edge и Kestrel подтверждены HTTP `403`, HTTPS login `200`, WSS SignalR handshake, `403` для прямого spoofed HTTPS и для HTTP от доверенного прокси. Порт Kestrel на хосте не публиковался, JWT в access/error-выводе прокси не найден. [Nginx](../deploy/nginx/chat-backend.conf), [настройка](../README.md#production-за-nginx). |
| FILE-01 | Документы сохраняются как `PENDING`, проверяются по формату и отправляются в ClamAV. Чистые получают `READY`, неверный формат или обнаружение угрозы переводят в `QUARANTINED`. Сбой сканера оставляет `PENDING` с повтором. Для PDF дополнительно проверяются окончание и диапазон смещения startxref. Миграция `VerificationDocumentScanning` помещает старые документы в `PENDING`. | OPS-01 | Минимальный SDK — `10.0.403`, оба framework в `chat.Api.runtimeconfig.json` требуют `10.0.14` с разрешённым обновлением patch. Доступность внешних сервисов проверяется отдельно. |

Проверка EF Core подтвердила соответствие модели snapshot. OpenAPI обновлён до `0.2.1`, маршруты и JSON-поля сохранены. Ограничения на скачивание и одобрение отражены в контракте. [OpenAPI](../artifacts/openapi.json), [REST-контракт](contracts/api-v1.md).

## P1 — высокий приоритет перед публичным запуском

### TLS-01. Production принимает пароль и выдаёт JWT по HTTP при отсутствии HTTPS-порта

**Воспроизведено.** Kestrel в `Production` слушал только loopback HTTP, HTTPS-порт отсутствовал. После миграции `POST /v1/auth/login` с временной учётной записью администратора вернул HTTP `200` и токены по незашифрованному соединению. При отсутствии HTTPS-порта `UseHttpsRedirection` пропускает запрос, а `UseHsts` не защищает первый HTTP-запрос. Схема TLS за обратным прокси также влияет на WebSocket/SSE, поскольку query-токен принимается только при `Request.IsHttps`. До внешней публикации нужно ограничить прямой доступ к Kestrel, зафиксировать TLS на входе и доверенные forwarded headers, затем проверить HTTP и WSS в целевой топологии. [Program.cs](../src/chat.Api/Program.cs#L50), [BootstrapServices.cs](../src/chat.Api/DependencyInjection/BootstrapServices.cs#L112), [Microsoft Learn](https://learn.microsoft.com/aspnet/core/security/enforcing-ssl#port-configuration).

### FILE-01. Документ верификации доступен администратору без сканирования

**Воспроизведено.** Невредоносные байты с префиксом `%PDF-`, без валидной структуры PDF, приняты с `200`. После привязки к заявке администратор скачал их с `200`. Чужой доступ ограничен, выдача идёт как вложение с `nosniff`, но B02 проверяет только размер и префикс и не вызывает ClamAV или карантин. Проверяющий может открыть произвольное содержимое под видом документа. Для рабочего контура нужен отдельный статус сканирования и запрет выдачи до безопасного результата. [BusinessDrafts.cs](../src/chat.Api/Businesses/BusinessDrafts.cs#L43), [BusinessEndpoints.cs](../src/chat.Api/Endpoints/BusinessEndpoints.cs#L41), [требования безопасности](security.md#верификация-бизнеса).

### OPS-01. В среде аудита установлен устаревший shared runtime

**Подтверждено по версиям.** `dotnet --list-runtimes` показал `Microsoft.AspNetCore.App 10.0.5` и `Microsoft.NETCore.App 10.0.5`. Например, advisory CVE-2026-56170 перечисляет ASP.NET Core Runtime для Windows x64 до `10.0.5` включительно. Успешный аудит NuGet не проверяет установленный runtime. Версия production неизвестна. Перед запуском следует подтвердить актуальный security patch .NET 10 на целевом хосте и повторить проверки на нём. [Microsoft security advisory](https://github.com/dotnet/aspnetcore/security/advisories/GHSA-j8gr-8fp3-5q5h), [список исправлений .NET 10](https://github.com/dotnet/core/blob/main/release-notes/10.0/cve.md).

## P2 — дефекты и риски эксплуатации

1. **DB-01. Readiness сообщает о готовности до миграций.** На чистой PostgreSQL воспроизведены `GET /health/ready → 200` и `POST /v1/auth/login → 500`. Probe проверяет соединение. Вход и refresh отдельно могут вернуть `503` при отсутствующем ключе JWT, хотя readiness остаётся зелёным. Нужен жёсткий барьер применения миграций и проверки обязательной конфигурации перед допуском трафика. [PostgresHealthCheck.cs](../src/chat.Api/Endpoints/PostgresHealthCheck.cs#L9), [AccountCredentials.cs](../src/chat.Api/Identity/AccountCredentials.cs#L37).
2. **API-01. Экспорт неполон для генерации клиентов.** Upload документов не объявляет обязательный заголовок `X-Application-Draft`. В OpenAPI отсутствуют фактические `404` каталога, диалогов и файлов, `409` модерации и `MEDIA_NOT_READY`, `413/415` верификационного upload и `503` входа/refresh при отсутствующем ключе. Health, напротив, описывает `429` при отключённом rate limiting. Выходные роли и состояния представлены строками без enum. Тест сравнивает два экземпляра одного описания и поэтому пропускает эти расхождения. [OpenAPI](../artifacts/openapi.json), [ApiDocumentation.cs](../src/chat.Api/Endpoints/ApiDocumentation.cs#L32), [BusinessEndpoints.cs](../src/chat.Api/Endpoints/BusinessEndpoints.cs#L17), [OpenApiTests.cs](../tests/chat.ContractTests/OpenApiTests.cs#L35).
3. **BIZ-01. Отклонённая заявка продолжает блокировать повторную подачу.** Уникальность `(Country, RegistrationNumber)` и email действует для всех статусов. Отклонение сохраняет компанию и владельца. Гость с подходящим по формату документом может занять реквизиты до проверки, а отклонение их не освобождает. Кроме того, `409` позволяет отличить занятый email или номер от свободного, даже если точное поле не указано. Нужен согласованный процесс восстановления доступа и повторной подачи, учитывающий историю модерации. [BusinessConfiguration.cs](../src/chat.Infrastructure/Persistence/BusinessConfiguration.cs#L12), [BusinessService.cs](../src/chat.Api/Businesses/BusinessService.cs#L58), [BusinessService.cs](../src/chat.Api/Businesses/BusinessService.cs#L169).
4. **AUTH-01. Защита входа ограничена IP и памятью процесса.** Распределённые попытки обходят счётчик по адресу, а за прокси адрес без доверенной пересылки может быть общим. Проверка PBKDF2 для известного аккаунта выполняется под `FOR UPDATE`, поэтому целевые попытки задерживают вход, refresh и сброс этого аккаунта. Нужны нагрузочная проверка и лимиты по аккаунту и доверенному клиентскому IP. [IdentityServices.cs](../src/chat.Api/Identity/IdentityServices.cs#L40), [BootstrapServices.cs](../src/chat.Api/DependencyInjection/BootstrapServices.cs#L53), [AccountService.cs](../src/chat.Api/Identity/AccountService.cs#L32).
5. **AUTH-02. Повтор refresh после потери ответа отзывает рабочую сессию.** Это выбранная модель защиты от replay. Если параллельные запросы используют один старый токен или первый ответ теряется после commit, второй запрос отзывает семейство. Клиентам нужно сериализовать refresh и корректно обрабатывать повторный вход. Тест подтверждает последовательный replay. Гонку двух refresh и потерю ответа отдельно не воспроизводили. [AccountService.cs](../src/chat.Api/Identity/AccountService.cs#L71), [RFC 9700, §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2).
6. **SYNC-01. REST не восстанавливает прочитанное состояние второй стороны.** `GET /conversations/{id}` и `GET .../messages` не возвращают сохранённые receipts. `POST .../read` возвращает только сторону вызывающего. После пропущенного `ConversationReadUpdated` клиент восстановит историю сообщений, но не состояние прочтения собеседника. Потребуется согласованное изменение контракта либо явное ограничение семантики reconnect. [MessageContracts.cs](../src/chat.Contracts/Messaging/MessageContracts.cs), [ConversationEndpoints.cs](../src/chat.Api/Endpoints/ConversationEndpoints.cs#L19), [ConversationService.cs](../src/chat.Api/Messaging/ConversationService.cs#L161).
7. **RT-01. Событие отзыва имеет отдельный путь без проверки живой сессии.** `BusinessAccessRevoked` адресуется по всем сохранённым membership компании, включая неактивные, и по локальному списку соединений. Ветка отправляет `businessId` и причину до проверки JWT-семейства в периодическом обходе. Обычные сообщения проходят проверку получателей. Прямой отзыв membership разрывает соединение, но эта ветка публикуется только для suspension. Уведомление о suspension на клиентскую сторону также не отправляется. [OutboxWorker.cs](../src/chat.Api/Messaging/OutboxWorker.cs#L101), [BusinessService.cs](../src/chat.Api/Businesses/BusinessService.cs#L181).
8. **RT-02. Ограничение на один экземпляр API.** Реестр подключений локален, тогда как `SKIP LOCKED` назначает событие одному worker. При двух репликах worker может завершить событие на реплике, где нет адресата. На одной реплике периодический обход делает запросы на каждое соединение и подписку. Лимиты по числу подключений и подписок отсутствуют. Срок отзыва зависит от скорости обхода и очереди. [OutboxWorker.cs](../src/chat.Api/Messaging/OutboxWorker.cs#L34), [RealtimeConnections.cs](../src/chat.Api/Messaging/RealtimeConnections.cs#L27), [README](../README.md#вложения-и-push).
9. **MEDIA-01. Выданная ссылка остаётся действительной после отзыва ACL.** После suspension тест подтверждает `404` на выдачу новой ссылки. Уже выданный GET URL является bearer-доступом к S3 до минуты. Между проверкой ACL и созданием URL также есть окно гонки. Аналогично выданный PUT работает до пяти минут и пишет только во временный ключ. Это ограниченный остаточный доступ, который нужно учитывать при формулировке гарантий отзыва. [MediaService.cs](../src/chat.Api/Messaging/MediaService.cs#L79), [AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html#PresignedUrl-Expiration).
10. **MEDIA-02. Сканирование и хранение требуют эксплуатационных гарантий.** Без сканера файл необратимо помечается `QUARANTINED` для этого upload. Исключение при сетевой ошибке оставляет `PENDING` и приводит к `500`, повтор запроса возможен. Ошибка протокола сканера, возвращённая текстом вместо `OK`, также превращается в карантин. При сбое БД после копирования в `media/` возможен объект без готовой записи. Очистка незавершённых, карантинных и готовых непривязанных объектов не покрыта сквозным тестом и зависит от жизненного цикла хранилища и уборки записей. [ClamAvFileScanner.cs](../src/chat.Infrastructure/Media/ClamAvFileScanner.cs), [MediaService.cs](../src/chat.Api/Messaging/MediaService.cs#L39), [README](../README.md#вложения-и-push).
11. **OPS-02. Внешние вызовы держат блокировки PostgreSQL.** Отправка SignalR выполняется до commit обработчика Outbox, HTTP-запрос к Expo выполняется под блокировками устройства, пользователя и бизнеса. При медленном шлюзе или клиенте это задерживает изменение ACL и увеличивает время обработки. Повтор после принятия запроса внешним шлюзом и до сохранения результата может дать дубли push. [OutboxWorker.cs](../src/chat.Api/Messaging/OutboxWorker.cs#L54), [PushWorker.cs](../src/chat.Api/Messaging/PushWorker.cs#L36).
12. **OPS-03. SMTP-очередь теряет письма при сбоях.** Регистрация и reset фиксируют изменения в БД отдельно от ограниченной очереди процесса. Переполнение, перезапуск и SMTP-ошибка могут оставить пользователя с `202` и без письма. README описывает повтор через вход или повторный запрос. В целевом контуре нужен мониторинг ошибок доставки и согласованная гарантия повторов. [AccountEmailDelivery.cs](../src/chat.Api/Identity/AccountEmailDelivery.cs#L26), [AccountService.cs](../src/chat.Api/Identity/AccountService.cs#L129).

## P3 — целостность, сопровождаемость и пробелы покрытия

- **Целостность на уровне БД.** FK диалога на `Users` не проверяет `UserKind`. FK attachment и read receipt на `MessageId` не связывают этот ID с тем же `ConversationId`. HTTP-обработчики проверяют эти условия, но миграции, импорт или прямые записи могут обойти их. [MessagingConfiguration.cs](../src/chat.Infrastructure/Persistence/MessagingConfiguration.cs), [DeliveryConfiguration.cs](../src/chat.Infrastructure/Persistence/DeliveryConfiguration.cs#L8).
- **Устойчивость пагинации.** Курсор inbox опирается на изменяемый `UpdatedAt`. При новом сообщении между запросами диалог может переместиться в уже пройденную часть списка. Для истории сообщений используются неизменяемые `CreatedAt` и `Id`. Невалидный 32-символьный cursor отдельно вернул `400`. [ConversationService.cs](../src/chat.Api/Messaging/ConversationService.cs#L40), [CursorPage.cs](../src/chat.Api/Endpoints/CursorPage.cs#L11).
- **Retention.** Worker удаляет только истёкшие незакрытые черновики. Политика для старых refresh-сессий, завершённых Outbox и push, поданных документов и записей вложений в коде не найдена. Outbox сохраняет копии текста сообщений. Нужны сроки хранения, учёт резервных копий и согласованная очистка метаданных и объектов. [ExpiredDraftWorker.cs](../src/chat.Api/Businesses/ExpiredDraftWorker.cs#L16), [Outbox.cs](../src/chat.Api/Messaging/Outbox.cs#L16), [модель данных](data-model.md).
- **Устройства.** Регистрация повторно предъявленного Expo-токена меняет владельца и семейство сессии через upsert. Это позволяет переключить аккаунт на одном устройстве, но при утечке токена позволяет переоформить регистрацию и помешать доставке прежнему владельцу. [DeviceEndpoints.cs](../src/chat.Api/Endpoints/DeviceEndpoints.cs#L23).
- **CI и границы слоёв.** Workflow проверяет сборку, тесты и снимок OpenAPI. Самостоятельных проверок breaking changes, секретов, SAST, Docker-образов и кросс-клиентского SignalR в workflow нет. При этом большая часть use cases и orchestration сейчас в `chat.Api`, а `chat.Application` содержит в основном порты, что расходится с целевой разбивкой. [backend.yml](../.github/workflows/backend.yml), [testing-and-release.md](testing-and-release.md#ci-quality-gates), [architecture.md](architecture.md#модульный-монолит).
- **Охват проверки.** Нужны отдельные негативные сценарии для неверных issuer/audience/expiry JWT, параллельного refresh, JWT через фактический TLS-прокси, `LeaveConversation`, `SetTyping`, payload `ConversationReadUpdated` и доставки `BusinessAccessRevoked`. Текущий аудит не повторял smoke JS-клиента, не проверял React Native или синхронизацию контрактов с consumer-репозиториями. Реальные MinIO и ClamAV проверены на чистом объекте и несовпадении MIME, сигнатурный тест с вредоносным образцом не проводился.
