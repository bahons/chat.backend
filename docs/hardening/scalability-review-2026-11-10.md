# Проверка архитектуры, кода и масштабирования — 10 ноября 2026

Проверена рабочая копия `chat-backend` на базе `1513891`: конфигурация приложения,
авторизация REST/SignalR, операции диалогов и вложений, очереди, миграции и индексы,
очистка данных, тесты и deployment. Исходная рабочая копия была чистой.

**Вывод:** модульный монолит с PostgreSQL и transactional Outbox подходит для дальнейшего
развития. Текущая реализация рассчитана на один Production-процесс и ограничивает realtime
256 подключениями. Горизонтальное масштабирование пока не реализовано. Проверка кода
и интеграционные тесты не устанавливают предельную пропускную способность production.

## Выполненные оптимизации

| Изменение | Причина и результат |
| --- | --- |
| `ConversationService.CreateAsync`: `FOR SHARE` вместо эксклюзивной блокировки компании | Раньше создание любого диалога занимало `FOR UPDATE` на компании. Оно конфликтовало с `FOR SHARE` у отправки сообщений и сериализовало создание разных диалогов одной компании. Теперь параллельные операции совместимы; suspension по-прежнему ждёт завершения транзакции. |
| Параметризованный `INSERT ... ON CONFLICT (ClientUserId, BusinessId) DO NOTHING` | Уникальный индекс разрешает гонки создания одной пары. Последующий отдельный SELECT при стандартном READ COMMITTED видит зафиксированного победителя. Повтор возвращает существующий диалог без изменения его времени или содержимого. |
| Предикат `ConversationId` в запросах вложений истории и повторной отправки | Запрос использует обе колонки существующего индекса `(ConversationId, MessageId)`, создаваемого для составного FK. Раньше фильтр содержал только вторую колонку. Изменение создаёт условия для эффективного доступа по индексу; конкретный выбор плана и выигрыш времени требуют EXPLAIN на представительном объёме. |
| Outbox обрабатывает очередь до опустошения | Убрана квота 25 событий на секундный проход. При быстрых операциях она ограничивала среднюю обработку примерно 25 событиями/с, то есть 12,5 текстовыми сообщениями/с при двух событиях на сообщение, без учёта receipts и повторов. Теперь пауза в секунду применяется только после отсутствия работы или ошибки прохода. Обработка остаётся последовательной, с отдельным scope на запись и прежними lease, fencing, ACL и retry. |

Изменения сохраняют REST 0.5.0 и SignalR eventVersion 1. Новая миграция не требуется.
Ускоренное опустошение Outbox может увеличить нагрузку на PostgreSQL и SignalR при
накопленной очереди; фактическая скорость ограничена последовательной обработкой и I/O.
Внешние ошибки отдельных записей по-прежнему откладывают повтор через `AvailableAt`.

## Оставшиеся ограничения по приоритету

### P1 — горизонтальное масштабирование требует общего протокола доставки

`Program.cs` включает `SingleReplicaGuard` в Production. Второй API на той же БД отклоняется,
а потеря advisory lock останавливает процесс. Это согласованная защита текущего baseline.
`RealtimeConnections` содержит локальный реестр, а `OutboxWorker.DispatchAsync` выбирает
получателей из `connections.Snapshot` и завершает событие как `offline`, если их нет локально.

Одного добавления Redis backplane недостаточно: dispatcher по-прежнему не узнает о
подписках на других узлах. Сначала нужен протокол публикации события всем обслуживающим
узлам с проверкой актуального ACL перед локальной доставкой либо общий реестр адресации
с эквивалентными гарантиями. Отзыв сессии/membership и отказ общей инфраструктуры должны
закрывать доступ на каждом узле. Обязательны тесты двух API: подписчик на другом узле,
reconnect, повтор события, suspension, logout и потеря узла/координатора.
После этого можно менять guard и deployment. Для обычного SignalR с Redis нужно также
настроить sticky sessions; исключение с WebSockets-only и SkipNegotiation требует проверки
обоих потребителей. [Microsoft: SignalR hosting and scaling](https://learn.microsoft.com/en-us/aspnet/core/signalr/scale?view=aspnetcore-10.0).

### P1 — скорость retention недостаточна для постоянного потока сообщений

После исходного аудита ограничение количества партий и недостающие индексы устранены
в [этапе retention](retention-throughput-2026-11-10.md). Расчёт ниже описывает прежний
baseline. Новый предел зависит от настроенных бюджетов и фактической скорости PostgreSQL;
нагрузочное подтверждение остаётся открытым.

`RetentionWorker` удаляет максимум 200 строк каждой таблицы раз в 10 минут. Даже при
включённом `Retention:Approved` это максимум 28 800 Outbox-записей в сутки. Один message
создаёт две записи: уже при постоянной скорости выше 14 400 сообщений в сутки, без receipts,
retry и простоев, зрелый хвост Outbox будет расти. Например, 1 сообщение/с создаёт
172 800 событий/сутки и оставляет не менее 144 000 лишних строк/сутки после выхода retention
на установившийся режим. Это расчёт из кода, не результат нагрузочного теста.

Нужны повторные ограниченные партии с бюджетом времени, проверкой legal hold между партиями
и метрикой самого старого просроченного элемента. В модели отсутствуют индексы очистки
`(CompletedAt, Id)` у завершённых очередей и `(ExpiresAt, Id)` у refresh-сессий: текущие
частичные индексы рабочих очередей покрывают только незавершённые записи. Проверить планы,
затем добавить согласованную миграцию индексов с оценкой блокировок; при больших объёмах
рассмотреть секционирование. Политика retention и legal hold в этой задаче не менялась.

### P2 — лимиты и отзыв состояния привязаны к одному процессу

`LoginAttemptLimiter` хранит счётчики аккаунта и адреса в памяти. Global/auth HTTP limiters
тоже локальные. При N репликах фактический общий допуск может вырасти примерно в N раз.
Нужен атомарный общий лимитер с TTL, общим Retry-After и определённым поведением при отказе;
добавление backplane само по себе этого не решает. Текущий лимит realtime — 256 соединений
на API, 4 на пользователя и 16 подписок на соединение. Это программные ограничения,
не измеренная производительность сервера; менять их следует после нагрузочного прогона.

### P2 — внешнее I/O удерживает некоторые DB-блокировки

В `MediaService.CompleteAsync` запись проверенного объекта в S3 выполняется внутри
транзакции после эксклюзивной блокировки диалога. Операция может занимать до 10 секунд
и задерживать сообщения, receipts и другие complete этого диалога. В
`VerificationDocumentScanner` транзакция с row lock живёт во время сканирования ClamAV
с бюджетом до 15 секунд и удерживает подключение PostgreSQL.

Следующая оптимизация — короткий claim с lease/generation, внешнее I/O после commit,
затем условное завершение с повторной проверкой ACL, срока, retirement и владения lease.
Для S3 необходимы идемпотентные ключи и уборка потерянных объектов. Просто перенести I/O
за транзакцию без этих проверок нельзя: появятся гонки complete, send и cleanup.

### P2 — очереди и ресурсы нужно масштабировать совместно

- `PushWorker` имеет квоту 25 операций за двухсекундный проход, включая проверку receipts;
  SMTP — 16 за секундный проход. Последовательные внешние вызовы могут дополнительно
  снижать скорость. Нужны метрики lag/throughput и ограниченный параллелизм по ресурсам,
  с сохранением fencing. Outbox-оптимизация не снимает эти ограничения.
- Outbox admission выполняет подсчёт до 10 000 pending-строк для нового сообщения/receipt.
  Проверка и вставка не сериализованы глобально: это мягкий порог нагрузки, а не строгая
  общая квота при конкурентных writers. При высокой нагрузке измерить стоимость подсчёта
  и разработать admission без глобального узкого места.
- Push fanout ограничен 256 устройствами и текущим свободным объёмом очереди 10 000.
  Остаток не ставится на дальнейшую доставку; worker пишет событие 229 и полагается на REST.
  При росте нужны порционная постановка с durable continuation и отдельные метрики пропуска.
- Документы верификации до 5 МиБ сохраняются в PostgreSQL. Рост увеличивает объём WAL,
  backup и restore. До переноса в private object storage определить миграцию доказательств,
  проверку целостности и совместное восстановление DB/S3.

### P3 — границы слоёв и наблюдаемость

Большая часть use cases и EF-транзакций сейчас находится в `chat.Api`; `Application`
в основном содержит интерфейсы и построение сообщений. Следующие изменения переносить
по одному сценарию в Application с сохранением явных границ транзакций и ACL-тестов.
Разделение на микросервисы сейчас не устраняет перечисленные ограничения.

Есть структурированные backlog-логи, но нет полноценного контура измерений:
latency REST p50/p95/p99, lock wait, pool wait, DB round trips, pending/oldest age/dispatch
duration/dead letters, число соединений/подписок, длительность ACL sweep и GC/allocations.
Без этих данных нельзя обосновать число пользователей или размер серверов.

## Автоматические проверки

Новые `ScalingTests` работают с реальным PostgreSQL 17 через Testcontainers:

1. Восемь конкурентных create для двух клиентов одной компании завершаются при уже
   удерживаемом `FOR SHARE` на компании и дают ровно один диалог на клиента.
2. Незавершённая suspension конфликтует с create; после commit suspended-бизнес
   возвращает 404 и диалог не создаётся. Проверяется реальная ошибка PostgreSQL 55P03,
   обёрнутая execution strategy Npgsql.
3. 60 доступных Outbox-записей завершаются до первого idle delay. Управляемый TimeProvider
   фиксирует первую паузу; тест не сравнивает скорость с произвольным wall-clock порогом.

## План измерений перед увеличением нагрузки

На выделенном staging подготовить синтетические данные с большой историей сообщений,
вложениями и разным размером inbox компаний. Снять EXPLAIN (ANALYZE, BUFFERS) для истории,
вложений, inbox, каталога, admission и retention. Затем проверить ступенчатую нагрузку
создания диалогов и сообщений: сначала распределённую по компаниям, затем одну горячую
компанию/диалог. Повторить с realtime и push, с медленным S3/ClamAV и со сбоями зависимостей.
Сопоставить входящий поток со скоростью обработки и очистки после прогрева очередей.

Нагрузочный benchmark, долговременный soak, multi-node failover, SAST, сканирование
runtime-образа и целевой Production в этой задаче не проверялись. S3, SMTP и ClamAV в
интеграционных тестах представлены существующими тестовыми адаптерами; PostgreSQL настоящий.
Приёмочные SLO и целевое количество пользователей требуют согласованного профиля нагрузки.

Обоснование блокировок и upsert сверено с
[PostgreSQL 17: row-level locks](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS)
и [INSERT / ON CONFLICT](https://www.postgresql.org/docs/17/sql-insert.html).
Рекомендация проверки планов и порядка составного индекса соответствует
[Microsoft: efficient querying](https://learn.microsoft.com/en-us/ef/core/performance/efficient-querying).
